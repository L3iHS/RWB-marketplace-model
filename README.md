# RWB Marketplace Model

Решение кейса хакатона RWB «Модель маркетплейса: от корзины до выкупа».

**Репозиторий команды:** [L3iHS/RWB-marketplace-model](https://github.com/L3iHS/RWB-marketplace-model).

**Задание и окружение организаторов:** [daniilivanovp-droid/hackathon-students](https://github.com/daniilivanovp-droid/hackathon-students).
Копия задания лежит в [docs/handout.md](docs/handout.md) и [docs/tasks.md](docs/tasks.md),
происхождение материалов — в [docs/source/provenance.md](docs/source/provenance.md).

## Цель

Построить модель данных маркетплейса Capibara, на основе которой аналитики смогут получать согласованные и проверяемые показатели продаж, покупателей, продавцов и исполнения заказов.

Исходные данные — восемь выгрузок [Olist](https://github.com/olist/work-at-olist-data), 550 759 строк за 2016–2018 годы. Использование датасета регулируется лицензией CC BY-NC-SA 4.0, указанной организаторами.

## Архитектура

- `raw` — исходные данные без изменений; все поля загружаются как текст.
- `core` — типизированная модель с явными ключами, связями и уровнем детализации.
- `mart` — готовые наборы для отчётов поверх `core`.
- `ops` — история приёма полных снимков, опубликованные версии и текущий указатель.

Основной стек — PostgreSQL 16 и SQL. Python используется для загрузки, выгрузки ответов и тестов. Локальное окружение запускается через Docker Compose.

**Дашборд:** [y.cloud-path.ru](https://y.cloud-path.ru) — серверная демонстрация;
[localhost:3000](http://localhost:3000) после локального запуска backend/frontend.
[Инструкция и показатели](docs/dashboard.md), [история категорий и адресов](docs/history.md),
[записка о решениях](docs/decisions.md).

**С чего начать:** [docs/model.md](docs/model.md) — устройство модели и схема,
[docs/answers.md](docs/answers.md) — ответы и контрольные цифры.

## Быстрый старт

Нужен только **Docker** (Docker Desktop на Windows и macOS, Docker Engine
с плагином compose на Linux). Python, psql и библиотеки живут внутри контейнера,
поэтому команды одинаковые на любой ОС.

```bash
git clone -b dev https://github.com/L3iHS/RWB-marketplace-model.git
cd RWB-marketplace-model
docker compose run --rm app setup    # скачать данные и загрузить raw
docker compose run --rm app build    # собрать core и mart, 28 проверок внутри
docker compose run --rm app check    # сверить ответы с контрольными цифрами
docker compose run --rm app test     # модель, API, история, контроли и отказы
docker compose up -d --build backend frontend  # дашборд http://localhost:3000
```

Первый запуск дольше: Docker скачивает образы и собирает образ проекта (~1–2 минуты).

Все команды:

| Команда | Что делает |
|---|---|
| `setup` | Проверяет SHA-256 восьми CSV фиксированной версии Olist, скачивает отсутствующие/повреждённые и загружает `raw`. Повторно не перезаливает; `setup --reload` — перезалить |
| `build` | Собирает `core` и `mart` с нуля одной транзакцией; при ошибке остаётся прежняя модель |
| `check` | Сверяет ответы с контрольными цифрами задания |
| `test` | Тесты: настоящая выгрузка + искусственные крайние случаи во временной базе |
| `answers` | Показывает ответы и публикует полный комплект CSV/JSON, SQL и manifest в `artifacts/runtime/answers/`; `--output-dir ПУТЬ` задаёт другой каталог |
| `preview` | Первые строки каждой таблицы `core` и `mart` в виде pandas; `preview -n 10 -t orders` |
| `explore` | Разведка `raw`: ключи, пропуски, связи, деньги |
| `profile` | Профиль `raw` в `artifacts/profile.json` |
| `sql ФАЙЛ…` | Выполнить SQL-файлы, например `sql answers/02_top_sellers.sql` |
| `demo-init` | Создать отдельную новую `marketplace_demo` с исходной моделью |
| `simulate` | Создать пять полных снимков с вымышленными заказами и сменой статусов |
| `batch-manifest КАТАЛОГ --source-id ID --sequence N` | Проверить внешние CSV и опубликовать manifest готового снимка |
| `ingest КАТАЛОГ` | Проверить, архивировать и атомарно опубликовать новый полный снимок |
| `schedule` | Опрос каталога, один пакет за цикл; `--once` или ограничение `--max-runs` |
| `ingestion-status` | Текущая версия данных и история последних попыток |

Каждая команда пишется после `docker compose run --rm app`.
Справка: `docker compose run --rm app --help`.

### Новые данные и демонстрация

```bash
docker compose run --rm app demo-init
docker compose run --rm app simulate
docker compose run --rm -e PGDATABASE=marketplace_demo app schedule --interval-seconds 2 --max-runs 5
docker compose run --rm -e PGDATABASE=marketplace_demo app sql scripts/sql/demo_status.sql
```

Генератор воспроизводит пять дней: новые заказы, повторные покупки, доставки,
задержки и отзывы. Загрузчик принимает полные снимки через тот же путь, что и
внешние данные. Исходная `marketplace` и её `raw` сохраняются; демонстрация работает
в отдельной БД. Планировщик по умолчанию выключен, приведённый запуск конечный.
[Сценарий показа, входной контракт и расписание](docs/ingestion.md).

Обычная загрузка выполняется через `ingest`. `build` возвращает модель к исходному
`raw` и снимает указатель импортированной версии, сохраняя историю публикаций.

### Сохранённые результаты

`artifacts/answers/` содержит проверенный эталон исходной выгрузки.
Команда `answers` публикует новые результаты отдельно: она печатает каталог
поколения в `artifacts/runtime/answers/generations/`. Файл `current.json`
указывает на последний успешно подготовленный комплект. Внутри — CSV ответов 1–10,
`results.json`, точный SQL и `manifest.json` с хешами файлов, данных и схемы БД.

Ошибка SQL или записи до публикации сохраняет прежний указатель и результаты.
Предыдущие поколения не перезаписываются. Для чтения комплекта нужно один раз
открыть `current.json` и затем использовать указанный в нём каталог.
[Формат результатов и происхождение](docs/answers.md#сохранение-комплекта-ответов).

Начать с чистого листа (удалить базу вместе с данными):

```bash
docker compose down -v
```

**Подключиться к базе** из DBeaver или DataGrip: `localhost:5433`, база `marketplace`,
логин и пароль `hack` / `hack`. Порт 5433 выбран, чтобы не мешать базе
организаторов на 5432. Наружу база не открыта — только с этой машины.

**Без Docker** тоже можно: `python run.py build`, если на машине есть Python 3.11+
с пакетами из `requirements.txt` и `psql`, а база доступна по `PGHOST` / `PGPORT`.

## Структура

```
run.py      единая точка входа: все команды выше
model/      SQL-сборка core и mart из raw, выполняется по порядку имён одной транзакцией
answers/    ответы на вопросы аналитиков и сверка с контрольными цифрами
tests/      интеграционные тесты модели
explore/    разведка raw, в сборку не входит
docs/       модель, ответы, проблемы в данных, стратегия, задание
scripts/    загрузка raw, выгрузка ответов, просмотр таблиц, подключение к базе
artifacts/  эталонные ответы и профиль; новые поколения — в runtime/ (в Git не включаются)
Dockerfile, docker-compose.yml   окружение: база и контейнер проекта
```
