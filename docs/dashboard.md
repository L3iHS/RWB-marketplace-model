# Дашборд аналитика

Собственный интерфейс React/TypeScript получает готовые расчёты из FastAPI и
PostgreSQL. Аудитория — аналитик маркетплейса; руководитель использует подготовленные
показатели и выгрузки. Основной путь: выбрать период/штат → найти изменение →
посмотреть категории, продавцов или доставку → проверить заказы → выгрузить срез.

## Запуск

```bash
docker compose run --rm app setup
docker compose run --rm app build
docker compose up -d --build backend frontend
```

Открыть [дашборд](http://localhost:3000). API: [проверка готовности](http://localhost:8000/api/health),
[описание HTTP](http://localhost:8000/docs). Приложение доступно на локальных портах;
готовые образ, SSL и вход для публичного сервера требуют отдельной настройки.
Планировщик не запускается вместе с интерфейсом. Его сценарий — [отдельная инструкция](ingestion.md).

## Экраны и показатели

| Раздел | Вопрос аналитика | Расчёт и уровень |
|---|---|---|
| Обзор | Сколько продали, сколько заказов доставили, как меняется динамика? | Оборот = сумма goods_amount доставленных заказов; число доставленных = число таких заказов; динамика — по месяцу покупки с календарём |
| Продажи | Что формирует оборот и кто покупает повторно? | Продавец/категория — сумма цены своих единиц доставленных заказов; покупатели — distinct customer_unique_id всех статусов выбранного среза; повторные — люди с двумя и более заказами в срезе |
| Доставка | Где сроки хуже и насколько полны даты? | Только доставленные заказы; средний срок = среднее числа календарных дней от покупки до вручения; доля поздних = поздние / заказы с обеими датами доставки; пропуски дат показываются отдельно |
| Качество | Какие исходные проблемы влияют на интерпретацию? | Число проблем и затронутых сущностей по severity/issue_code/entity_type из mart.quality_issues; область — весь набор |
| Детали | Какие конкретно заказы стоят за срезом? | Одна строка mart.order_totals на заказ; на экране последние 50 всех статусов, выгрузка — весь выбранный срез |
| Ответы 6–10 | Какие результаты получены для блока Б? | Фиксированные SQL answers/06–10, вопрос 9 в двух разрезах; результаты, SQL и CSV без фильтров дашборда |
| История | Почему прошлые категории и адреса не меняются? | Наблюдаемые версии категории и ссылка позиции, снимок адреса заказа и сравнение с текущим профилем |

Обзор содержит короткие таблицы и переходы к деталям. Длинные результаты
листаются страницами, вопросы 6–10 переключаются по одному: прокрутка страницы
не заменяет навигацию. Название продукта — «Аналитика маркетплейса».

Средний чек = среднее order_amount доставленных заказов: товары **с доставкой**.
Оборот = стоимость товаров **без доставки**, BRL; он не является доходом/прибылью площадки.
Число единиц и число строк чека различаются: строка — товар/продавец внутри заказа.
История категории берётся из версии, закреплённой за позицией, адрес — из снимка заказа.

## Фильтры и согласованность

Дата с/по относится к оформлению заказа, верхняя граница включительна.
Штат — адрес покупателя на момент заказа. Пустые фильтры означают всю историю;
качество отдельно помечено как глобальное и от фильтров продаж не меняется.
Числовые эталоны задания нужно сравнивать при соответствующих правилах и периодах:
для вопроса 1 — сентябрь 2016 — август 2018, для вопроса 4 — вся история/все статусы.

Один GET /api/dashboard читает контекст и все блоки одной REPEATABLE READ READ ONLY
транзакцией. Frontend отображает результат и не пересчитывает бизнес-агрегаты.
Десятичные суммы передаются строками. CSV-выгрузка использует те же фильтры и ожидаемый
ID версии; если данные обновились, API возвращает 409 и предлагает обновить экран.
В интерфейсе различимы исходный набор, синтетический и внешний снимок.

Пустой срез показывает 0 для сумм/количеств и отсутствие значения для среднего/доли
без знаменателя. Отсутствующая дата не считается своевременной доставкой.
Ошибки подключения и загрузки показываются явно, без подстановки примерных цифр.

## Какие показатели нельзя складывать

- Средний чек, срок доставки, доли и проценты пересчитываются по общим числителям
  и знаменателям; сумма/среднее средних по штатам даёт другой результат.
- Один покупатель может покупать в разных месяцах и штатах: суммы distinct по
  группам не равны distinct всего набора. Повторные покупатели также неаддитивны.
- Заказ с несколькими продавцами/категориями входит в несколько групп: их числа
  заказов не складываются в общее число заказов. Стоимость собственных позиций складывается.
- Топ продавцов — часть оборота; сводка качества содержит проблемы, а не уникальные
  заказы всего набора. Одна сущность может иметь несколько проблем.

SQL-редактор и сохранённые исследования остаются следующим этапом продукта.
Текущий интерфейс предназначен для фиксированных общих показателей и срезов.

## Демонстрация по кнопке

Во вкладке «Демонстрация» кнопка «Загрузить следующий день» запускает ровно один
полный снимок через тот же `ingest`. Фоновая работа ограничена этим нажатием;
регулярный worker `schedule` не включается. Интерфейс опрашивает только статус.
Подготовка первой серии может занять больше времени, чем последующие шаги.

Показ использует отдельную `marketplace_demo_dashboard`, оригинал не пересобирается.
После первого дня доступен переключатель «Исходные / Демонстрационные» для всех
просмотров и CSV. Переход сбрасывает фильтры; текущая версия видна на экране.
На третьем дне синтетический товар получает новую категорию, а профиль первого
синтетического заказа — новый адрес. В истории можно сравнить текущие значения
со значениями, зафиксированными для старых позиций и заказов.

API: GET `/api/demo/status`, POST `/api/demo/advance` (202), повтор во время
обработки — 409. Параметр `dataset=original|demo` выбирает только один из двух
разрешённых источников; пользовательские пути и произвольные имена БД не принимаются.
Состояние опубликованных дней сохраняется в БД и восстанавливается после перезапуска.
Существующая БД и серия не перезаписываются; для повторного показа с первого дня
нужно заранее подготовить отдельный чистый демонстрационный экземпляр.
