# Находки по сырым данным

Получены запросами из `explore/01_profiling.sql` (номера разделов совпадают).
Каждая находка — что увидели и что из этого следует для модели.

## Ключи таблиц (раздел 2)

| Таблица | Ключ | Комментарий |
|---|---|---|
| orders | `order_id` | уникален |
| order_items | `(order_id, order_item_id)` | `order_item_id` — номер внутри заказа, не id |
| order_payments | `(order_id, payment_sequential)` | уникален |
| order_reviews | `(review_id, order_id)` | ни `review_id`, ни `order_id` по отдельности не уникальны |
| products | `product_id` | уникален |
| sellers | `seller_id` | уникален |
| customers | `customer_id` | уникален, но это **не человек**, см. ниже |
| category_translation | `product_category_name` | уникален |

## Покупатель (раздел 5)

- `customer_id` выдаётся **на каждый заказ**: у каждого `customer_id` ровно один заказ.
- Настоящий человек — `customer_unique_id`: 96 096 людей на 99 441 `customer_id`.
  У одного человека бывает до 17 `customer_id`.
- **Для модели:** измерение покупателя строим по `customer_unique_id`,
  а `customer_id` оставляем как атрибут заказа (адрес доставки может
  отличаться от заказа к заказу).

## Статусы и выручка (разделы 3, 4)

- 97% заказов `delivered`, остальные — в пути, отменены или недоступны.
- **Проверено:** выручка из контрольной цифры (13 221 498.11) — это
  `sum(price)` по позициям заказов в статусе `delivered`, **без доставки**
  (`freight_value`), за сентябрь 2016 — август 2018.
- У 8 заказов `delivered` нет даты вручения, а у 6 заказов не в статусе
  `delivered` она есть. Статус и даты не всегда согласованы.
- **Для модели:** правило «что такое выручка» фиксируем в одном месте
  (флаг `is_revenue` или представление), а не повторяем в каждом запросе.

## Уровень позиций (раздел 8)

- Одна строка `order_items` — **одна единица товара**. Если купили 3 одинаковых
  товара, будет 3 строки с одинаковыми `product_id`, ценой и доставкой.
- 112 650 единиц, но 102 425 различных «строк чека» (заказ + товар + продавец).
- В 1 278 заказах больше одного продавца (до 5).
- **Для модели:** факт позиций на уровне единицы товара, количество = число строк.
  Выручка продавца считается по его позициям, не по сумме заказа.

## Связи (разделы 6, 7)

- Ссылки из позиций, платежей и отзывов ведут на существующие заказы,
  товары и продавцов: сирот нет.
- 775 заказов без позиций: почти все `unavailable` (603) и `canceled` (164).
  Обычный `JOIN` с позициями их потеряет. Для выручки это не страшно,
  для подсчёта заказов по статусам — страшно.
- 1 доставленный заказ без платежа, 768 заказов без отзыва.

## Категории (раздел 9)

- 610 товаров без категории.
- 2 категории (13 товаров) отсутствуют в справочнике перевода:
  `pc_gamer`, `portateis_cozinha_e_preparadores_de_alimentos`.
- **Для модели:** пустую категорию заменяем явным значением (например,
  `unknown`), перевод берём через `LEFT JOIN` с запасным вариантом
  из португальского названия. Иначе сумма по категориям не сойдётся с общей.

## Пустые месяцы (раздел 10)

- В ноябре 2016 заказов нет вообще, в сентябре и декабре 2016 и
  сентябре–октябре 2018 их единицы.
- **Для модели:** нужен календарь (`dim_date`), отчёты по периодам строим
  от него через `LEFT JOIN`, иначе пустой месяц пропадёт из отчёта.

## Деньги: позиции против платежей (раздел 11)

- У 98 299 из 98 665 заказов сумма платежей = `price + freight`
  с точностью до копейки, у 366 расходится (ваучеры, проценты рассрочки).
- 3 платежа с типом `not_defined` и нулевой суммой.
- **Для модели:** платежи — отдельный факт на своём уровне, выручку от них
  не считаем. Расхождение можно показать как метрику качества данных.

## Прочие странности (разделы 12–14)

- 1 359 заказов переданы в доставку раньше подтверждения оплаты.
- 383 позиции с бесплатной доставкой, 9 платежей на ноль.
- Отзывы: 547 заказов с несколькими отзывами, 789 `review_id`
  на нескольких заказах.
- Города написаны вразнобой: `sao paulo`, `sp`, `sao paulo - sp`, `sao paulop`.
  Для отчётов по географии надёжнее штат (`state`), чем город.
