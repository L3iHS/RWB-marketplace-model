# Новые данные и демонстрация обновлений

Система принимает **полные снимки восьми CSV** и обновляет текущие `core`/`mart`.
Исходные файлы `data/*.csv` и схема `raw` сохраняются. Дневные изменения без
предыдущей истории не являются полным снимком и не принимаются как замена модели.

## Показ на синтетических данных

```bash
# Новая отдельная БД; существующую БД команда не перезаписывает.
docker compose run --rm app demo-init

# Пять полных снимков: по 20 новых заказов в день, seed=42.
docker compose run --rm app simulate

# Пять циклов с паузой в две секунды, затем процесс завершается.
docker compose run --rm -e PGDATABASE=marketplace_demo app schedule --interval-seconds 2 --max-runs 5

# История публикаций и изменение показателей.
docker compose run --rm -e PGDATABASE=marketplace_demo app ingestion-status
docker compose run --rm -e PGDATABASE=marketplace_demo app sql scripts/sql/demo_status.sql

# Сохранить SQL/CSV/контекст уже обновлённой модели.
docker compose run --rm -e PGDATABASE=marketplace_demo app answers --output-dir artifacts/runtime/demo-answers

# Эталонная БД marketplace по-прежнему проходит исходные числовые контроли.
docker compose run --rm app check
```

В DBeaver: `localhost:5433`, БД `marketplace_demo`, пользователь/пароль `hack`.
Пауза в две секунды идёт **после завершения обработки**, поэтому публикация полного
снимка занимает дополнительное время. Смена модельного дня здесь ускорена;
техническое время публикации остаётся настоящим.

Генератор добавляет вымышленные заказы после последнего наблюдаемого события в
исторических заказах и отзывах. Исторические CSV-строки копируются побайтно;
исходные файлы не переписываются. Между днями появляются новые заказы, адресные
профили, повторные покупки известных людей, доставки и отзывы. Есть отменённые
заказы, доставка вовремя и с задержкой, несколько единиц товара и разделённые
платежи. Новые ID имеют префикс `syn_`. Отменённые заказы не создают продажи;
возвраты денег не моделируются, поскольку в контракте нет событий возврата.

Это **демонстрационные операции поверх Olist**, не данные и не подключение к WB.
Поле `kind=synthetic` сохраняется в публикации и контексте выгрузки.
`artifacts/runtime/incoming/simulation.json` описывает seed, базовые SHA-256,
даты, число заказов и статусы каждого дня. Параметры можно менять:

```bash
docker compose run --rm app simulate --days 7 --orders-per-day 100 --seed 17 --output-dir artifacts/runtime/another-feed
```

Те же исходники и параметры дают те же CSV и идентификаторы; время создания
manifest меняется. Готовый каталог генератор не перезаписывает.
Для повторного показа с первого дня создайте новую БД:
`demo-init --database marketplace_demo_replay`, затем передавайте её через
`-e PGDATABASE=marketplace_demo_replay`. Одну и ту же серию можно использовать
в нескольких независимых демонстрационных БД.

## Входной контракт

Каждый каталог пакета содержит ровно восемь CSV с исходными именами/заголовками
и `manifest.json`. CSV — UTF-8, допускается BOM. Manifest версии 1:

```json
{
  "format_version": 1,
  "snapshot_type": "full",
  "kind": "external",
  "source_id": "marketplace-export",
  "sequence": 1,
  "created_at": "2026-10-28T10:00:00+00:00",
  "files": {
    "olist_orders_dataset.csv": {"rows": 99441, "bytes": 123, "sha256": "..."}
  }
}
```

В реальном manifest перечислены **все восемь** файлов, размеры и хеши настоящие.
`sequence` — возрастающий номер полного снимка одного `source_id`, не дата заказа.
Смена источника и откат истории требуют отдельного явного решения.
Увеличение номера само по себе не создаёт новую версию, если данные не изменились.

Источник сначала завершает запись CSV, затем публикует manifest. Для подготовки
внешнего снимка есть команда проверки и запечатывания:

```bash
docker compose run --rm app batch-manifest artifacts/runtime/incoming/batch-001 --source-id marketplace-export --sequence 1
docker compose run --rm app ingest artifacts/runtime/incoming/batch-001
```

Пути внутри Docker относятся к `/app`; файлы под каталогом проекта доступны через
bind mount. При нативном запуске допустимы обычные локальные пути.
Команда `batch-manifest` сигнализирует готовность атомарным появлением manifest.
После этого производитель не изменяет пакет. Незавершённые каталоги без manifest
планировщик пропускает. Настоящий адаптер API/S3/SFTP должен сначала подготовить
такой каталог; коннектора к внешнему источнику в текущей реализации нет.

## Проверки и публикация

1. Загрузчик захватывает общую PostgreSQL advisory lock. Второй получает `busy`.
2. Создаёт попытку в `ops.ingestion_attempts`, копирует файлы в собственный архив,
   проверяет заголовки, количество полей/строк, размеры, SHA-256, типы и ключи.
   Диагностика CSV содержит файл, строку и поле; FK проверяет PostgreSQL с таблицей,
   ключом и именем ограничения.
3. Загружает копию во временные таблицы. Проверяет, что ранее опубликованные ключи
   заказов, позиций, платежей и отзывов не исчезли.
4. В одной транзакции заменяет строки стабильных таблиц `core` через `DELETE`/`INSERT`,
   выполняет общие `02_load.sql` и 26 инвариантов `90_checks.sql`. Представления
   продолжают ссылаться на те же таблицы; `DROP SCHEMA` и `TRUNCATE` здесь нет.
5. Записывает `ops.dataset_versions` и указатель `ops.current_dataset`. **COMMIT —
   единственная точка публикации** данных и версии.

При отказе до COMMIT сохраняются прежняя модель и указатель; диагностика попытки
записывается отдельно. Архив проверенного входа сохраняется даже при отказе SQL.
Повтор текущего сочетания данных/SQL преобразования/схемы даёт `skipped`.
Известный прошлый набор или меньший номер — `stale_batch`, без отката модели.
После перезапуска незавершённые попытки отмечаются как прерванные. Повтор после
потери подтверждения COMMIT находит уже записанную версию и не дублирует факты.

Метаданные фиксируют SHA-256 входных CSV, SQL-шаблонов преобразования и проверок,
фактической схемы, происхождение, архив и сводку изменений/качества. Изменение
схемы или преобразований после публикации блокирует обычную загрузку: требуется
явная пересборка или будущий механизм миграций. Автоматических миграций здесь нет.

Аналитический клиент читает контекст и данные в одной `REPEATABLE READ READ ONLY`
транзакции: старый запрос видит старую модель, новый после COMMIT — новую.
Так уже работает `answers`; его manifest дополнен `context.publication`.
Основание: [изоляция PostgreSQL 16](https://www.postgresql.org/docs/16/transaction-iso.html)
и [блокировки](https://www.postgresql.org/docs/16/explicit-locking.html).

`build` — отдельная операция: пересобирает модель **из исходного raw** и снимает
указатель текущего импортированного набора. История публикаций/архивы остаются.
Для регулярного поступления данных используется `ingest`, а не `setup --reload`
или `build`. Числовые эталоны `check` относятся к исходному Olist; новые снимки
должны проходить инварианты, но не обязаны сохранять исходные суммы.

## Планировщик

`schedule --once` обрабатывает один следующий пакет и завершается. Без `--once`
worker повторяет цикл с интервалом `--interval-seconds` (по умолчанию 86400 секунд).
Первый цикл начинается сразу; это интервал от завершения цикла, а не фиксированный
запуск в полночь. `--max-runs N` ограничивает число циклов, включая пустые.

Пакеты сортируются по источнику и номеру; каталог предназначен для одного потока.
За цикл обрабатывается один пакет. История попыток хранится в БД, поэтому перезапуск
не требует файла локального курсора. Отказавший пакет с тем же manifest не вызывает
бесконечный повтор: оператор исправляет/заменяет снимок и запускает `ingest` явно.
Следующий полный снимок может восстановить поток. Логи — JSON в stdout;
`ingestion-status` показывает текущую версию и последние 20 попыток.

Для необязательного серверного режима добавлен профиль Compose:

```bash
# По умолчанию использует marketplace_demo; обычный compose up его не включает.
docker compose --profile ingestion up -d scheduler
docker compose logs -f scheduler
docker compose stop scheduler
```

Сервис не установлен в системное расписание и не имеет автоматического restart.
Для другой БД задаётся `PGDATABASE`, для интервала — `INGEST_INTERVAL_SECONDS`
через окружение Compose или локальный `.env`. SIGTERM/SIGINT останавливают worker;
активная публикация завершается, а принудительное прекращение откатывает транзакцию.

Полные снимки и полная замена дают простую воспроизводимость ценой диска, WAL и
времени загрузки. Инкременты, политика хранения архивов, роли доступа и подключение
к реальному источнику требуют дальнейшей эксплуатационной работы.
