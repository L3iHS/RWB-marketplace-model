# Обоснование архитектуры и подготовка к защите

## Почему такое решение

Это обоснованный выбор под условия кейса, а не доказанно лучшая архитектура
для любого маркетплейса. Цель: сохранить детализацию, получать правильные
ответы, принимать неизвестные вопросы и объяснить код на защите.

| Альтернатива | Когда уместна | Почему выбрали иначе |
|---|---|---|
| Одна плоская таблица из всех исходников | Набор действительно одного уровня | Две позиции и два платежа дают четыре комбинации; суммы размножаются |
| Только пять готовых агрегатов | Требования фиксированы и детализация доступна отдельно | В середине появятся неизвестные вопросы; понадобятся исходные факты |
| Звезда с отдельными фактами заказа, позиции, платежа | Основной продукт — BI с устойчивыми измерениями | Тоже корректное решение; нормализованный core проще сопоставить с источником, а BI-уровень вынесен в mart |
| Нормализованный core + витрины | Нужны целостность и разные уровни аналитики | Наш вариант: понятные сущности, FK/PK и удобные агрегаты |

Одиннадцать таблиц не являются обязательным минимумом. Справочники статусов
и типов платежей можно заменить проверками, а уникального покупателя —
вычисляемым представлением. Мы выделили их, чтобы закрепить связи и правила
и иметь место для будущих атрибутов. Отдельная таблица сущности покупателя
сейчас содержит только идентификатор; это осознанная небольшая избыточность.

## Пример предотвращённой ошибки

Заказ: товары 100 и 50, платежи 120 и 30. Прямой JOIN позиций и платежей
по order_id создаёт четыре строки. Сумма товаров станет 300 вместо 150.
В `mart.order_totals` сначала независимо получаем 150 по позициям и 150
по платежам, затем соединяем по одной строке на заказ.

## Ограничения, которые следует назвать

- Полное обновление с TRUNCATE держит блокировки; нет обновления без простоя.
- IF NOT EXISTS — повторное выполнение одной версии, а не миграции.
- category_id постоянен в пределах базы; перенос требует сохранения
  соответствий. Переименование без кода источника считается новой категорией.
- Состояние заказов — снимок. Историческое состояние на дату не восстановлено.
- Ключ review/order подтверждён этой выгрузкой, а не контрактом источника.
  Новые нарушения уникальности остановят сборку и потребуют пересмотра.
- Проверки доказывают заявленные свойства на выполненных сценариях,
  а не отсутствие любых возможных ошибок.

## Доказательства

- `scripts/check_scenarios.py`: 13 сценариев новых и ошибочных данных в
  изолированной базе, включая постоянство ключей и сохранение модели при отказе.
- `model/START_HERE.md` и `model/team_walkthrough.sql`: разбор для команды
  и пример опасного JOIN на реальном заказе.

- `scripts/check_model.py`: повторная сборка, сравнение содержимого core/raw,
  контрольные ответы и откат искусственной ошибки.
- `model/results/`: полные результаты пяти вопросов.
- `mart.quality_issues`: исходные идентификаторы проблемных сущностей.
- `model/build.sql`: порядок выполнения этапов и граница транзакции.

## Сценарий выступления на 3–4 минуты

### 0:00–0:40. Проблема и результат

«Capibara получила отдельные выгрузки заказов, товаров, платежей и отзывов.
Разные уровни данных и разные правила расчёта давали несовместимые отчёты.
Мы построили модель из 11 связанных таблиц и три удобных представления.
Исходные данные сохраняются, отчёты считают из core и mart».

Показать схему из README. Объяснить четыре факта: заказ, единица товара,
платёжная запись, отзыв. Объяснить, почему они не объединены в одну таблицу.

### 0:40–1:20. Ключи и детализация

«В 99 441 заказе оказалось 96 096 уникальных покупателей. Устойчивый ключ
человека отличается от customer_id адресной записи. Мы сохранили оба уровня.
Позиция уникальна внутри заказа, поэтому её ключ составной. У платежа тоже
составной ключ; review_id сам по себе не уникален».

Показать соответствующие таблицы/связи. Не перечислять все колонки.

### 1:20–2:00. Главная аналитическая ошибка

Открыть блок 5 из `model/team_walkthrough.sql`. На текущем снимке выбранный
заказ имеет стоимость товаров 298,90 и две платёжные записи. Прямой JOIN
позиций и платежей даёт 597,80 — ровно вдвое больше.

«Наше представление независимо суммирует позиции и платежи до уровня заказа.
Поэтому добавление второго способа оплаты не увеличивает стоимость товаров».
Если выгрузка поменялась, использовать фактические результаты SQL, а не
заучивать эти суммы.

### 2:00–2:40. Правила и проверки

Показать первые пять результатов: выручка 13 221 498,11; первый продавец
226 987,93; средний чек 159,88; повторные оформления 3,12%; 74 категории.

«Выручка кейса без доставки, чек с доставкой. Отсутствующая категория входит
в отдельную группу. Пропуски дат и расхождения платежей видны с идентификаторами
в диагностике. Проверены повторы сборки, откат и 13 сценариев новых данных».

### 2:40–3:30. Польза и развитие

«Дашборд для руководителя продаж и операций связывает товарный оборот,
число заказов и исполнение доставки. Для каждого показателя определены
источник и уровень; средние, доли и уникальных покупателей нельзя складывать.
При росте сначала измеряем планы и блокировки; следующий шаг — сохранённые
агрегаты и загрузка изменений. Возвраты и отправления добавляются отдельными
сущностями. Историю, которой нет в исходнике, мы не выдумываем».

Завершить конкретной границей: текущая сборка пакетная, удерживает блокировки.
Отдельно назвать использование ИИ и фактически выполненные проверки.

## Короткие ответы для защиты

| Вопрос | Ответ и доказательство |
|---|---|
| Почему 11 таблиц? | Это выбранные сущности/справочники, а не обязательное число. Главная причина — разные уровни фактов и проверяемые связи |
| Почему не одна таблица? | JOIN нескольких связей один-ко-многим размножает суммы; реальный пример есть в walkthrough |
| Почему не звезда? | Звезда с разными фактами тоже допустима. Нормализованный core сохраняет источник, витрины дают удобство аналитики |
| Почему не удалить заказы без позиций? | Они существуют в источнике и важны для числа оформлений и качества; сумма по ним неизвестна |
| Почему delivered без даты остаётся в выручке? | Продажу определяет согласованное правило статуса. Для длительности доставки нужны даты — это другой показатель |
| Что будет с новым статусом? | Сохранится, появится предупреждение, в выручку автоматически не попадёт |
| Что будет с новой категорией? | Получит новый ключ; существующие ключи не меняются. Перевод можно добавить позже |
| Что будет с дубликатом платежа? | Сборка откажет с названием ключа, не удалит строку догадкой и сохранит прежний core |
| Чем логическая строка отличается от единицы? | В raw каждая запись — единица. В отчёте объединяем одинаковые товар/продавец/цену/доставку/срок внутри заказа; количество — число единиц группы. На delivered получаются средние 1,0385 строки и 1,1422 единицы; N09 воспроизводит 123,75 из подсказки |
| Почему платежи не равны сумме товаров? | Это независимые источники. Разницу показываем, не подгоняем; доставка учитывается при сопоставлении |
| Почему доля повторных включает отмены? | Это определение совпадает с контролем вопроса 4. Подписано как повторное оформление; успешные повторные покупки считаются отдельно |
| Можно ли сложить заказы продавцов? | Нет: один заказ может иметь нескольких продавцов; итог нужно считать distinct заново |
| Можно ли измерить воронку корзины? | Нет событий посещения и корзины; таких знаменателей в данных нет |
| Как доказали сохранность? | Ограничения БД, сравнение строк/сумм с raw, fingerprint raw/core, повторные и ошибочные сборки |
| Где история категорий и статусов? | Её нет в источнике. Постоянный ID категории не является историей изменения атрибутов |
| Что сделал ИИ? | Анализ, код, проверки и черновики материалов. Команда обязана понимать и принимать решения; вклад описан в ai_usage |
