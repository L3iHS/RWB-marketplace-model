## Команды перед сдачей

После загрузки raw и установки зависимостей, из корня репозитория.
Для notebook: `.venv/bin/python -m pip install -r requirements-notebook.txt`.

```bash
.venv/bin/python scripts/build_model.py
.venv/bin/python scripts/export_answers.py
.venv/bin/python scripts/run_notebook.py
.venv/bin/python scripts/package_submission.py --verify-clean
```

Архив появится в `dist/capibara-submission.zip`. Внутри есть `OPEN_FIRST.md`,
все материалы, notebook с выводами, HTML, графики, исходные скрипты, SQL-ответы,
CSV, отчёт проверки и SHA-256
файлов. Данные CSV источника (61 МБ), .venv и локальные настройки не включаются.
Их скачивание и установка описаны в README.

Также создаётся `dist/marketplace_model.sql` — один обычный SQL-файл со всей
сборкой и транзакцией. Его можно выполнять целиком как SQL-скрипт в DBeaver
на базе с заполненным raw. Файл собран из исходных SQL, бизнес-логика не
дублируется вручную. Если выполнение прервано, завершите транзакцию командой
`ROLLBACK;` перед повтором. Безопасный просмотр — через отдельные SELECT,
а не запуск сборки ради открытия данных.

Пакетировщик читает базу в read-only снимке, сверяет сохранённые CSV с текущими
запросами, проверяет контроль блока А и соответствие номеров вопросов/ответов.
При появлении нового номера в docs/tasks.md без SQL-ответа упаковка остановится.
Для notebook проверяются исполнение всех ячеек, отсутствие ошибок и соответствие
исходного кода/текста версии, после которой сохранены выводы и HTML.
После изменения notebook его нужно переисполнить, затем обновить архив.
Опция `--verify-clean` дополнительно загружает CSV в отдельную временную
базу без предварительного ANALYZE и проверяет единый SQL с контролями блока А;
время сборки записывается в отчёт, база затем удаляется. Для этой опции нужны
локальные CSV и право CREATEDB. Без неё пакетировщик проверяет только готовую
рабочую модель и файлы комплекта, не выполняя новую сборку.
Контрольные числа блока А относятся к текущему снимку Olist; при изменении
самой выгрузки проверять новые цифры нужно отдельно.

## Репетиция команды

1. Один участник объясняет сущности и гранулярность, второй — расчёты и качество,
   третий — дашборд и развитие. Если участников меньше, блоки объединяются.
2. Каждый участник должен уметь ответить про ключ покупателя, составной ключ
   позиции, отличие выручки от чека и размножение строк при JOIN.
3. Проверки на новых данных выполняются отдельно:
   `.venv/bin/python scripts/check_scenarios.py`.
4. Проверка полного снимка и отката:
   `.venv/bin/python scripts/check_model.py`.

Проверки уже выполнялись агентом. Понимание участниками и фактическую
репетицию нельзя отметить выполненными автоматически.
